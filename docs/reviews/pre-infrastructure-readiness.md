# Подготовка приложения перед инфраструктурой

Дата: 23.10.2026. План: [экономное развёртывание на VPS](../plans/2026-10-22-2044-feat-vps-production-deployment-plan.md).

Кодовая часть U1–U4 подготовлена и проверена локально. Можно переходить к U5–U6 — Docker-поставке и CI/GHCR. Это не разрешение публичного запуска: ресурсная приёмка, Linux-образы, настоящий HTTPS и восстановление из внешней копии ещё впереди. Полные критерии готовности U1–U4, зависящие от этих проверок, пока не закрыты.

## Что изменилось

| Этап | Результат в приложении |
| --- | --- |
| U1: runtime и сборка | Сборка Turbopack использует публичные placeholders и недоступную БД. Контент, canonical, robots и sitemap вычисляются при запросе. Проверяются HTTPS-origin и runtime-секреты; ограничены пулы web/worker/migrator. Добавлены liveness/readiness и проверка записи медиа при старте. |
| U2: загрузка | HTTP multipart сохраняется в серверный temp-файл; оригинал копируется потоково и финализируется атомарно. Сохранён лимит 500 MiB, согласованы request/file/field limits. Добавлены pending-маркеры, проверяемая очистка непринятых оригиналов и устаревшего staging. |
| U3: обработка | Стратегия видео выбирается перед encoder: совместимый H.264/AAC remux-ится, остальное кодируется с ограничениями. Worker получает ограниченные повторы, graceful shutdown, heartbeat, эксклюзивный lock и восстановление задач. Receipt позволяет повторно использовать уже готовые производные после сбоя до записи CMS. |
| U4: схема и данные | Добавлена initial migration с запретом применения к занятой схеме и разрушительного down. Подготовлен data-only импорт с dry-run, проверками schema parity, FK, ID/sequences, очереди и SHA-256 файлов. Dev migration ledger не переносится; неизвестная схема, совпадающие source/target и непустое назначение отвергаются. |

Production schema push выключен; dev push выполняет только web. Worker не запускает introspection/DDL: это устранило обнаруженное в браузерной проверке исчерпание его небольшого пула соединений.

Публичное чтение контента имеет явную request-границу перед draft mode. Повторная сборка с прогретым кешем не пытается читать CMS. Sitemap кеширует относительные пути, чтобы один артефакт можно было запускать с разными runtime-доменами.

Версии существующих библиотек не обновлялись. `pg` и `@types/pg` стали прямыми зависимостями с уже имевшимися в lockfile версиями. Новые кодовые файлы декомпозированы и проходят лимит 300 строк; SQL initial migration разбит на упорядоченные части без изменения сгенерированного DDL.

## Проверки и свидетельства

Среда: macOS arm64, Node.js 22.22.0, pnpm 10.12.4, настоящая PostgreSQL в локальном Docker, Sharp и FFmpeg/ffprobe 8.0. Это не Linux- и не cgroup-приёмка.

| Проверка | Результат |
| --- | --- |
| `pnpm check` | PASS: Biome, лимит 300 строк, Next route types, TypeScript, Stylelint, токены, **116 unit-тестов**. Генерация route types использует build-контекст и работает с HTTP-адресом домашнего dev-стенда. |
| `pnpm test:media` | PASS: **13 тестов** с настоящими файлами и обработчиками. Проверены неизменность оригиналов, temp/Buffer-пути, недоверенный путь и symlink, streaming-копирование, очистка staging, timeout, remux без изменения H.264-потока, поворот и SAR. |
| Полный `pnpm test:e2e` | PASS: **65 сценариев**, включая менеджера, черновики, предпросмотр, публикацию, доступ, фото/видео и интерфейс. После последнего изменения request-границы повторены `site.spec.ts`, `api-workflows.spec.ts`, `admin-media.spec.ts`: **7 PASS**. |
| `NEXT_OUTPUT_DIR=.next-verification pnpm build` | PASS: Turbopack, TypeScript, prerender и traces; рабочая БД недоступна сборке. Повторная сборка с прогретым кешем прошла без чтения CMS. |
| Анализ артефакта | В **837 файлах** server/static не обнаружены значения реального `PAYLOAD_SECRET` и пароля БД; **17 трассировок** не включают `.env` и private-каталоги. Это проверка Next-артефакта, не будущих Docker-слоёв. |
| Миграции и bootstrap | Чистая БД → initial migration → повторный migrate → первый владелец; повторное создание владельца и миграция поверх dev ledger отвергаются. |
| Репетиция импорта | Сопоставлены **151 таблица и 56 файлов**; dry-run и apply, контроль содержимого, версий, публикации, владельца, связей и следующих ID. Неподдерживаемая очередь, одинаковые source/target, повторный импорт в непустую БД и другая схема отвергаются. |
| Production smoke | Одна сборка запущена с двумя runtime-origin: canonical/robots/sitemap используют текущий адрес. Без БД live остаётся `200`, ready возвращает ограниченный по времени `503` без внутренних подробностей. |
| HTTP multipart | Принят файл **64 MiB**, превышающий прежний неявный предел parser 50 MiB. Оригинал закрыт для гостя; лишний файл отвергнут. При искусственной ошибке БД непринятый оригинал и parser temp очищены. |
| Worker lifecycle | Второй worker не получает lock. SIGTERM даёт текущему обработчику 30 секунд, затем прерывает его; очередь и оригинал сохраняются, следующая попытка завершается. После имитации сбоя между финализацией производных и записью CMS используется прежний receipt/key. |
| Secret scan | Read-only Gitleaks с редактированием значений: совпадений в выбранных `src`, `scripts`, `tests` нет. Allowlist не создавался. |

Дополнительно разобран Fallow-снимок IDE: **80 предупреждений severity 4**, не ошибки компилятора. Удалены лишние модульные `export` у восьми значений и один неиспользуемый публичный тип. Повторяющийся 194-строчный union блоков был настоящим: генератор теперь создаёт общий `ContentBlock`, а `Page`, `Product`, `Project` и `Service` ссылаются на него. Это исправлено в postprocessor генерации, поэтому переживает повторный `pnpm payload:types`.

В повторном проходе устранены ещё несколько подтверждённых повторов: общие хуки страниц и выставочных материалов вынесены в одну настройку; проверка доступа к черновикам и guards повторной обработки заявок/медиа используют общие функции; обход медиассылок теперь один вместо двух; одинаковая сетка характеристик вынесена в общий CSS-модуль; E2E-помощник использует общий сценарий отправки и ожидания сохранения. Оставшиеся похожие участки в сгенерированных Payload-типах не менялись вручную; тёмные токены в разных media conditions также сохранены, так как они обслуживают разные режимы темы. Тестовый helper `ADMIN.root`, не имевший потребителей, удалён.

После этого рефакторинга прошли `pnpm lint`, `pnpm typecheck`, `pnpm lint:css` и unit-тесты (**117 тестов в 12 файлах**, отдельный тест медиа — **20 тестов**). Браузерный E2E-прогон после изменения helper не повторялся: текущий runner удаляет `.next-e2e` и `private/e2e-media`, а также пересоздаёт `promformatech_e2e`; перед таким запуском нужно убедиться, что там нет нужных пользовательских данных. Анализатор не подавлялся вслепую.

Расширенная репетиция запускается через `RUN_PRODUCTION_SMOKE=true pnpm test:integration`. Runner создаёт и удаляет только собственные случайные базы `promformatech_verification_*`; E2E использует отдельную `promformatech_e2e`. Рабочая локальная база и её медиа не менялись. Тестовое наполнение не является одобренным источником production-контента.

Локальные финальные протоколы находятся в `app/artifacts/pre-infrastructure/`: `check.log`, `build.log`, `integration.log`, `e2e-focused.log`, `build-inspection.json`. Каталог исключён из Git; исходники проверок входят в репозиторий и позволяют воспроизвести результат. Полный браузерный прогон и media-suite выполнены в этом проходе; финальные повторные логи относятся к указанным отдельным проверкам.

## Что ещё требуется перед выкатом

1. **U5–U6:** Linux production-images web/worker/migrator, совместимые UID/GID и volumes, native Sharp/FFmpeg, Docker build context без секретов/медиа, GHCR и CI. На VPS поставляется готовый артефакт; локальные pnpm-команды из инструкции не становятся способом production-обновления.
2. **Перенос реального наполнения:** выбрать и согласовать снимок владельца, сохранить исходную копию и повторить schema/data/media rehearsal на нём. В этой работе проверена изолированная фикстура. Автоматически выбирать рабочую БД источником запрещено.
3. **U7/U9:** настоящий домен, Nginx/TLS, proxy/body/timeouts, права preview и server actions через HTTPS. Два origin выше проверены на внутреннем HTTP upstream с Host/Origin; TLS они не проверяют.
4. **Ресурсы и тяжёлые входы:** cgroup memory peak/RSS/CPU на 2 vCPU / 4 ГБ, upload около/сверх 500 MiB, параллельный bulk, отмена/полный диск и самый тяжёлый разрешённый длинный 4K-исходник. Лимиты кода не доказывают вместимость VPS или максимальное время обработки.
5. **U8:** внешние согласованные копии БД/медиа/секретов, восстановление на чистом сервере, мониторинг диска, очереди, сертификата и копий. SQL и filesystem не образуют единую транзакцию: для неоднозначного обрыва импорта предусмотрены journal/receipt и ручная сверка, а не автоматическое восстановление поверх новых данных.
6. **Перед менеджером и публикацией:** закрыть тестовый доступ, подтвердить контакты и privacy, провести самостоятельную приёмку менеджером. SMTP остаётся необязательным: заявки сохраняются в CMS, доставка почты пока не подтверждена.
