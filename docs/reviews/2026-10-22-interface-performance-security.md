# Интерфейс, производительность и безопасность

Дата: 22.10.2026. Объект: локальное приложение `Promformatech/app`.
Это сайт промышленной компании с выставочным представлением продукции,
услуг и проектов. Корзина, складской учёт и отдельный глобальный store сейчас не нужны.

## Что сделано

- Добавлены скелетоны для загрузки содержимого и оболочки сайта. Основная
  область резервирует высоту; футер не занимает место будущего контента.
  Анимация отключается при системном предпочтении уменьшенного движения.
- Переключатель с солнцем/луной меняет светлую и тёмную темы; кнопка **T ↕**
  циклически меняет три размера текста. Нет видимых надписей, меню и модальных окон;
  есть подсказки, доступные названия и индикатор размера. До ручного выбора тема
  следует системе. Предпочтения сохраняются в cookie и читаются
  при серверном рендеринге. Сайт и админка имеют независимые предпочтения.
  В админке используется штатный ThemeProvider Payload. Поля формы не сбрасываются.
- Основной текст сайта увеличен минимум до 18 px при обычном масштабе,
  базовый rem админки — постоянные 15 px. Увеличение меняет только
  типографические токены, а не корневой rem, контейнеры и отступы.
- Hero восстановлен по композиции исходного сайта: фото заполняет весь баннер,
  текст и кнопка — поверх него, включая мобильный экран. Равномерный лёгкий
  слой зависит от темы; половина фото не закрыта заливкой. Исправлен
  контраст заголовков услуг и номеров этапов в тёмной теме.
- Ширина общего контейнера — весь экран до 1920 px, затем центрирование.
  Переключение размера текста не меняет этот предел. Заголовки услуг остаются
  в потоке, чтобы крупный текст не накладывался на изображение карточки.
- Палитры, размеры, радиусы и скелетоны описаны в источнике дизайн-токенов;
  CSS генерируется. Кнопка поиска скруглена; логотип читается на тёмном фоне.
- Русские подписи добавления заданы для получателей, офисов, контактных лиц,
  меню, ссылок подвала, характеристик изделия, этапов и строк характеристик блока.
- Встроен справочник `/admin/help`, пояснения разделов и ссылки на нужные главы.
  Инструкция открывается отдельно, чтобы не потерять несохранённые изменения.
- Изображения фасада используют `next/image`. Loader выбирает подготовленные
  WebP 480/960/1600 px; `sizes` соответствует карточке, колонке или первому экрану.
  Высота/ширина сохраняют пропорции до загрузки. Только первый hero получает
  приоритетную загрузку. Постер видео использует `Image unoptimized`.
- Внешний Gravatar заменён штатным аватаром Payload: тест обнаружил таймаут
  внешнего запроса. Исправлено переполнение шапки админки при крупном тексте
  на мобильном экране.
- Проверки медиа вынесены в `view-model.ts`: компоненты вызывают `isReadyImage`
  и `isReadyVideo`. Числовой ID связи обрабатывается один раз на границе CMS,
  компоненты получают узкую модель. Длинной цепочки условий внутри JSX-компонента нет.
- Добавлена основа переводов: типизированный русский словарь, provider сайта
  и связь с языком Payload. Тексты новых элементов и основных общих компонентов
  вынесены из JSX; CMS labels используют штатные локализованные значения.
  Объём переноса и оставшиеся шаги: [локализация](../architecture/localization.md).

## Настройки и организация приложения

Проверены установленные Next 16.4.2, React 19.3.0, Payload 3.91.0, TypeScript 5.9.3,
Base UI 1.9.0, Sharp 0.35.5 и текущие конфигурации. Версии зависимостей не менялись.

`withPayload` сохранён: он задаёт необходимую интеграцию с Next. Разработка и
сборка используют Turbopack. PostCSS обрабатывает общие CSS media-токены и не
заменяет сборщик. Biome проверяет TypeScript/JS, Stylelint — CSS. Локальный
шрифт не требует запросов к Google Fonts. GraphQL нужен интеграции Payload,
даже если фасад использует Local API; удалять peer-зависимости наугад не следует.

Публичный интерфейс и админка разделены route groups, CMS-схемы находятся в
`src/cms`, чтение и бизнес-функции — в `src/features`, переиспользуемый UI —
в `src/components/ui`, константы — в `src/config`. Новый функционал следует
этим границам; клиентские компоненты ограничены управлением видом и изображениями.
Проверка запрещает явный `any` и файлы длиннее 300 строк. Сгенерированные
типы Payload обновляются генератором, вручную не правились.

В Payload runtime принимает системную тему `auto`, хотя тип `setTheme`
описывает только светлую/тёмную. Это различие локализовано в `AdminAppearance`
и проверено браузером. При обновлении Payload нужен повтор этого сценария.
Нативные стили шапки также требуют повторной проверки после обновления CMS.

## Производительность: подтверждённое и требующее измерений

Готовые производные избавляют запрос страницы от повторного кодирования
изображений. Next Image используется с собственным loader, а не с публичным
кешем `/_next/image`: так сохраняется авторизация черновиков и отзыв доступа
после отмены публикации. Приватные ответы медиа намеренно не превращены в
публично кешируемые файлы ради формального результата Lighthouse.

Скелетоны улучшают состояние ожидания, но сами по себе не ускоряют SQL или SSR.
Данных для обещания конкретного улучшения LCP/TTFB пока нет. Следующий замер
нужно делать на production-сборке, с реальными фото и скоростью мобильной сети.

Кандидаты на последующую оптимизацию:

1. Измерить холодный и прогретый рендер главной, карточек, поиска и preview.
   Проверить последовательные независимые чтения настроек/контента и четырёх
   коллекций поиска; распараллеливать только после оценки нагрузки на PostgreSQL.
2. Проверить LCP-изображение, CLS, вес клиентского JS и количество SQL-запросов.
   Не подключать новые плагины и кэширование без измеримого узкого места.
3. На сервере ограничить память/CPU FFmpeg. Один worker ограничивает параллельную
   нагрузку, но длинное видео может задерживать другие задачи, включая почту.
   Отдельные очереди/worker для уведомлений нужны при подтверждённой задержке.
4. Перед несколькими экземплярами приложения проверить инвалидирование кеша
   опубликованных media-ссылок между процессами и после записей из CLI.
5. Разобрать `publishedMediaIDs` на смысловые шаги: источники опубликованных
   ссылок, сбор идентификаторов и кеширование. Это предложение пользователя
   на последующий рефакторинг. Перед изменением зафиксировать тестами доступ
   к производным, скрытые блоки, отмену публикации и инвалидирование кеша.

## Безопасность: границы проведённой проверки

Выполнен ограниченный статический проход по авторизации владельца/менеджера,
черновикам, preview, выдаче медиа, заявкам, лимитеру и обработке файлов. Отдельно
рассмотрены архитектурные границы. В просмотренных путях подтверждённых
уязвимостей не найдено. Это не полная сертификация безопасности приложения.

Проверены ограничения ролей, публикация отдельного снимка, приватные оригиналы,
проверка опубликованных ссылок для анонимной выдачи производных, фиксированные
варианты файлов, безопасные URL текста и вызов FFmpeg без shell. Настройки
видимости темы не влияют на права доступа. Исходники медиа сохраняются отдельно;
сжатие для публикации не обещает математически без потерь.

Не выполнялись эксплуатационные атаки, внешний нагрузочный тест, проверка
production-сервера, CVE/secret-сканирование Gitleaks/Semgrep и сканирование всех
зависимостей. Исходный Security-отчёт зафиксирован до UI-правок этой поставки;
он не означает повторного аудита каждой последующей строки.

Остаются вопросы, требующие окружения или решения владельца:

- **IP и reverse proxy.** При `TRUST_PROXY_HEADERS=false` лимитер использует
  общий источник. При включении proxy обязан перезаписывать `X-Real-IP`,
  а прямой доступ к origin должен быть закрыт. Иначе лимиты некорректны.
- **SMTP.** Проверить TLS-политику реального провайдера, доставку и восстановление
  пароля. Для STARTTLS определить необходимость `requireTLS`; текущие параметры
  сами по себе не доказывают ни утечку, ни гарантированное шифрование.
- **HTTPS и заголовки.** Проверить эффективные заголовки через внешний proxy,
  затем настроить HSTS/CSP с учётом Payload, встроенного preview и медиа.
  Отсутствие настройки в Next не доказывает её отсутствие на будущем proxy.
- **Медиа-процесс.** FFmpeg имеет лимиты и timeout, но не отдельную ОС-песочницу.
  В production ограничить права, доступ к секретам и ресурсы контейнера worker.

## Дизайн и наполнение: следующий полезный шаг

Сохранён текущий фирменный фасад. Теперь важнее доказать производственные
возможности компании, чем добавлять декоративные эффекты.

| Приоритет | Доработка | Критерий готовности |
|---|---|---|
| Перед запуском | Заменить тестовые/неподтверждённые контакты, заполнить правовую страницу | Владелец подтвердил данные; форма ведёт на опубликованную политику |
| Перед запуском | Наполнить проекты реальными кейсами | Задача → решение → результат, фото процесса и готового изделия; без придуманных клиентов и цифр |
| Перед запуском | Проверить материалы продукции и услуг | Понятно назначение, материал, процесс изготовления, применимость; у каждого есть качественное главное фото |
| Следующий этап | Уточнить главный призыв к действию | «Обсудить изготовление» / «Запросить расчёт» ведёт к короткой понятной форме |
| Следующий этап | Улучшить типографику длинных описаний | Сравнить нейтральный локальный шрифт для текста с текущим Unbounded; фирменный оставить в заголовках |
| Следующий этап | Унифицировать фотографии карточек | Единые пропорции и предсказуемое кадрирование; детали изделия не обрезаются |
| Следующий этап | Шаблоны заполнения для менеджера | Примеры хорошего описания, фото и кейса; подсказки для альтернативного текста и SEO |
| Позже | Приём чертежей и технических файлов | Утверждены форматы/лимиты, приватное хранение, проверка файлов и срок удаления |

Для админки предпочтительнее короткие пояснения рядом с полем, готовые блоки и
предпросмотр, а не новые панели с десятками параметров. Служебные настройки
остаются у владельца. Для приёмки менеджеру стоит самостоятельно изменить
контакты, создать материал, сохранить черновик, проверить телефон/планшет и
опубликовать — без помощи разработчика.

## План до публичного запуска

1. **Контент и приёмка.** Подтвердить контакты/политику, заполнить реальные
   кейсы, пройти сценарий менеджера и проверить физический телефон, Safari/Firefox.
2. **Один production-хост.** Docker-образы app/worker, PostgreSQL, reverse proxy,
   постоянные тома для БД/медиа, non-root, health checks, лимиты ресурсов,
   секреты окружения; миграции и откат релиза. Текущий Compose поднимает только БД.
3. **Восстановление.** Регулярные копии PostgreSQL и всего media-каталога,
   конфигурации/секреты отдельно; шифрование и копия на другом хосте, retention.
   Проверить восстановление в чистое окружение. Docker-том не является backup.
4. **Сеть и защита.** TLS, доверенный proxy, firewall origin, ограничения запросов,
   защита DDoS у провайдера/CDN. Лимитер приложения не защищает сетевой канал.
5. **Эксплуатация.** Контроль диска, очереди, доступности сайта и свежести backup,
   уведомления о сбоях, логи без секретов и с ограниченным хранением данных.
6. **Почта.** Подключить SMTP-провайдера и проверить доставку/повтор/сброс пароля.
   Собственный почтовый сервер не нужен для минимального запуска.
7. **Репозиторий и CI.** После подключения GitHub — проверки типов/стиля/тестов,
   проверка зависимостей и управляемые обновления. Полный сайт запускается на
   Node.js-хосте; GitHub Pages не запускает Payload/PostgreSQL/worker.

Точная оценка оставшегося срока зависит от готовности контента, доступа к хосту,
SMTP и объёма видео. Развёртывание считается завершённым после проверки
восстановления и пользовательской приёмки, а не после первого успешного запуска.
