# Домашний сервер: установка, запуск и обновление

Инструкция для тестового стенда ПромФормаТех на Ubuntu 24.04, актуальна на 22 октября 2026 года. Команды выполняются в Bash на домашнем сервере под обычным пользователем `alex`. Если команда завершилась ошибкой, остановитесь на этом шаге.

Это стенд для проверки сайта менеджером. Next.js работает в режиме разработки, PostgreSQL — в Docker, обработчик медиа — отдельным процессом Node.js. Production-сборка, Nginx, сертификат и домен для доступа внутри домашней сети не требуются. План публичного размещения описан [отдельно](../plans/2026-10-22-2044-feat-vps-production-deployment-plan.md).

## 1. Адреса и каталоги

| Параметр | Значение для текущего сервера |
| --- | --- |
| Код | `$HOME/apps/promformatech` |
| Приложение | `$HOME/apps/promformatech/app` |
| Репозиторий | `https://github.com/Stonek79/promformatech.git` |
| Ветка обновлений | `main` |
| Локальный IP | `192.168.1.130` — проверьте перед настройкой |

| Админка | `http://192.168.1.130:3001/admin` |
| Справка менеджера | `http://192.168.1.130:3001/admin/help` |
| PostgreSQL | `127.0.0.1:5433`, только на сервере |

Порт `3000` на текущем сервере занят другим проектом. Не останавливайте его контейнеры ради нашего сайта. У сервера уже есть Docker, VPN и другие сервисы: их переустановка и изменение маршрутов для этого стенда не нужны.

В примерах ниже IP соответствует текущей домашней сети. При другом IP замените его в `SERVER_URL` и ссылках. Желательно закрепить адрес за сервером в DHCP-настройках роутера.

## 2. Проверка установленного ПО

Если сервер уже настроен по переписке, начните с этой проверки и переходите к разделу 4 либо сразу к разделу 6 для существующего проекта.

```bash
cat /etc/os-release
uname -m
git --version
node --version
pnpm --version
docker --version
docker compose version
docker info --format '{{.ServerVersion}}'
ffmpeg -version | head -n 1
ffprobe -version | head -n 1
```

Версии проекта: Node.js указан в `app/.nvmrc` — сейчас `22.22.0`; pnpm указан в `app/package.json` — сейчас `10.12.4`. На текущем домашнем сервере уже запускался Node.js `22.22.2`; не переустанавливайте работающую среду только ради этой инструкции. Новую среду настраивайте по `.nvmrc`, а смену основной версии Node.js выполняйте отдельно от обычного обновления сайта.

## 3. Установка недостающего ПО

Этот раздел выполняется однократно, только для отсутствующих инструментов.

### Git, FFmpeg и вспомогательные утилиты

```bash
sudo apt update
sudo apt install -y git curl ca-certificates ffmpeg tmux
```

Пакет `ffmpeg` устанавливает и `ffprobe`. `tmux` пригодится, если нужно закрывать SSH-соединение, сохраняя работающий сайт.

### Docker Engine и Compose

Если `docker info` и `docker compose version` уже работают, пропустите установку. На сервере с существующими контейнерами не удаляйте Docker, `containerd`, сети и тома.

На чистой Ubuntu 24.04 с архитектурой x86_64 настройте официальный репозиторий:

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<'EOF'
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Architectures: amd64
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"
```

После добавления в группу выйдите из SSH и подключитесь заново, затем повторите `docker info`. Группа `docker` даёт широкие права управления сервером; добавляйте в неё только администратора. Для другой архитектуры или конфликтующей существующей установки используйте [официальную инструкцию Docker](https://docs.docker.com/engine/install/ubuntu/).

### Node.js

Если подходящий Node.js уже установлен, этот шаг пропустите. Для новой среды можно использовать [nvm](https://github.com/nvm-sh/nvm#installing-and-updating):

```bash
curl -fsSL https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.8/install.sh -o /tmp/promformatech-nvm-install.sh
bash /tmp/promformatech-nvm-install.sh
source "$HOME/.bashrc"
nvm install 22.22.0
nvm use 22.22.0
node --version
```

После клонирования репозитория команды `nvm install` и `nvm use` из каталога `app` читают версию из `.nvmrc`. В новой SSH-сессии при использовании nvm также выбирайте версию из этого каталога; это особенно важно, если на сервере несколько проектов.

### pnpm

Установите зафиксированную проектом версию, без `sudo`:

```bash
npm install --global --prefix "$HOME/.local" pnpm@10.12.4
export PATH="$HOME/.local/bin:$PATH"
grep -qxF 'export PATH="$HOME/.local/bin:$PATH"' "$HOME/.bashrc" ||
  printf '\n%s\n' 'export PATH="$HOME/.local/bin:$PATH"' >> "$HOME/.bashrc"
pnpm --version
```

Если после нового входа команда не находится, выполните `source "$HOME/.bashrc"`. Не устанавливайте случайную версию pnpm из пакетов Ubuntu поверх этой настройки.

## 4. Первая установка проекта

### Скачать код

Только если репозитория ещё нет:

```bash
mkdir -p "$HOME/apps"
git clone https://github.com/Stonek79/promformatech.git "$HOME/apps/promformatech"
cd "$HOME/apps/promformatech/app"
```

Для закрытого репозитория сначала настройте доступ к GitHub; токен нельзя помещать в URL команды клонирования. Если проект уже скачан, не клонируйте его повторно поверх существующего каталога: используйте раздел об обновлении.

### Зависимости и окружение

```bash
cd "$HOME/apps/promformatech/app"
pnpm install --frozen-lockfile
pnpm env:init
chmod 600 .env
```

`env:init` создаёт `.env` со случайными паролями и секретом Payload, но сохраняет уже существующий файл. Не копируйте `.env.example` поверх готового `.env` и не меняйте `PAYLOAD_SECRET` при каждом запуске.

Если pnpm сообщает об игнорировании build scripts, не разрешайте все скрипты подряд. Для известного `esbuild`, если его сборка действительно заблокирована, используйте `pnpm approve-builds`, выберите только `esbuild` и затем `pnpm rebuild esbuild`. Не коммитьте изменения политики зависимостей с сервера без проверки разработчиком.

Откройте окружение:

```bash
nano .env
```

Установите единственную строку:

```dotenv
SERVER_URL=http://192.168.1.130:3001
```

Остальные сгенерированные значения оставьте. Не показывайте содержимое `.env` в переписке и не добавляйте его в Git. Смена `POSTGRES_PASSWORD` в файле не меняет пароль уже созданного пользователя базы.

### Настройка Next.js для адреса стенда

В репозитории `next.config.ts` уже вычисляет разрешённые адреса из `SERVER_URL`. Для localhost, домашнего IP, домена или временного туннеля меняйте только эту переменную в `.env`, затем перезапускайте Next и worker. Редактировать конфиг на сервере не требуется.

Для `allowedDevOrigins` используется hostname без схемы и порта; для Server Actions — host с портом. Разрешается только выбранный адрес, без wildcard. Если переменная отсутствует или пуста, дополнительные разрешения не добавляются. Некорректный URL останавливает загрузку конфигурации: указывайте полный адрес со схемой, например `http://192.168.1.130:3001`. О механизме dev-доступа: [документация Next.js](https://nextjs.org/docs/app/api-reference/config/next-config-js/allowedDevOrigins).

### База и исходный контент

```bash
pnpm db:up
docker compose ps
pnpm seed
pnpm prepare:app
```

У PostgreSQL должен быть статус `healthy`. `seed` нужен при первом наполнении: он создаёт стартовые материалы и медиа, но не пользователя. В штатное обновление `seed` не входит.

При конфликте порта базы сначала выясните, кто его занимает. Если выбираете другой свободный порт, одновременно измените `POSTGRES_PORT` и порт внутри `DATABASE_URL` в `.env`; не останавливайте чужую базу.

### Создать владельца

Создавайте владельца до открытия стенда другим пользователям. Пароль вводится скрыто и не записывается непосредственно в команду:

```bash
read -r -p 'Почта владельца: ' OWNER_EMAIL
read -r -s -p 'Пароль владельца, минимум 16 символов: ' OWNER_PASSWORD
printf '\n'
OWNER_EMAIL="$OWNER_EMAIL" OWNER_PASSWORD="$OWNER_PASSWORD" pnpm cms:create-owner
unset OWNER_EMAIL OWNER_PASSWORD
```

Команда откажет, если владелец уже существует. После входа владелец создаёт отдельного пользователя с ролью менеджера в разделе «Пользователи». Общий аккаунт владельца менеджеру не передавайте.

## 5. Запуск сайта и worker

Откройте два терминала на сервере. Не запускайте одновременно несколько Next-процессов этого приложения в одном каталоге `.next`.

**Терминал 1 — сайт:**

```bash
cd "$HOME/apps/promformatech/app"
pnpm db:up
pnpm prepare:app
pnpm exec next dev --turbopack --hostname 0.0.0.0 --port 3001
```

Здесь намеренно используется `pnpm exec next dev`: стандартный `pnpm dev` в проекте привязан к `127.0.0.1`. Предварительный `prepare:app` генерирует токены, типы Payload и import map.

**Терминал 2 — фоновые задачи:**

```bash
cd "$HOME/apps/promformatech/app"
pnpm worker
```

Worker нужен для новых фото, видео и уведомлений. При его отсутствии сайт может открываться, но загруженные медиа будут ждать обработки. Для одного прохода очереди есть `pnpm worker:once`; для тестирования менеджером оставляйте обычный worker работающим.

**Проверка из ещё одного терминала:**

```bash
curl -I --max-time 20 http://127.0.0.1:3001
curl -I --max-time 20 http://127.0.0.1:3001/admin
```

После первой компиляции откройте на компьютере или телефоне из домашней сети:

- [Главная](http://192.168.1.130:3001).
- [Админка](http://192.168.1.130:3001/admin).

Переадресация админки на страницу входа допустима. В dev-режиме первое открытие раздела медленнее из-за компиляции. Это не замер production-производительности.

### Если нужно закрыть SSH

Вместо обычных терминалов можно открыть две именованные сессии:

```bash
tmux new-session -s promformatech-web
```

Внутри выполните команды запуска сайта выше. Отсоединиться, сохранив процесс: `Ctrl+B`, затем `D`. Во второй SSH-сессии аналогично создайте `tmux new-session -s promformatech-worker` и запустите worker. Повторно посмотреть терминал:

```bash
tmux attach-session -t promformatech-web
```

Либо `tmux attach-session -t promformatech-worker`. Сначала проверяйте `tmux ls`, чтобы не создать дубликаты. Для остановки подключитесь к нужной сессии и нажмите `Ctrl+C`. `tmux` переживает закрытие SSH, но не перезагрузку сервера; автозапуск web/worker пока не настроен.

## 6. Повторный запуск и остановка

После перезагрузки или остановки повторите раздел 5. Если зависимости уже установлены и код не менялся, повторные `install`, `env:init`, `seed` и создание владельца не нужны.

Для остановки нажмите `Ctrl+C` в терминале Next и worker. Дождитесь завершения текущей задачи worker, прежде чем копировать файлы или обновлять приложение.

Если база тоже больше не нужна работающей:

```bash
cd "$HOME/apps/promformatech/app"
pnpm db:down
```

Именованный том остаётся, при `pnpm db:up` данные вернутся. Не используйте `docker compose down --volumes`, `docker volume prune` или очистку всего Docker: они могут удалить данные этого и других проектов.

## 7. Резервная копия перед обновлением

Git хранит код, но не менеджерский контент. Нужны три части: база PostgreSQL, медиа и окружение/настройки. Копию делаем при остановленных Next и worker, чтобы база и файлы относились к одному состоянию. Другие программы не должны в этот момент писать в эту же базу или медиакаталог.

В одном терминале выполните блок ниже. База должна работать. Переменная `BACKUP_DIR` останется в этом терминале и пригодится далее:

```bash
BACKUP_DIR="$HOME/backups/promformatech/$(date +%Y%m%d-%H%M%S)"
(
  set -euo pipefail
  umask 077
  cd "$HOME/apps/promformatech/app"
  mkdir -p "$BACKUP_DIR"
  docker compose exec -T postgres sh -c \
    'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
    > "$BACKUP_DIR/database.dump"
  test -s "$BACKUP_DIR/database.dump"
  docker compose exec -T postgres pg_restore --list \
    < "$BACKUP_DIR/database.dump" > "$BACKUP_DIR/database-contents.txt"
  tar -czf "$BACKUP_DIR/files.tar.gz" .env next.config.ts compose.yaml private/media
  tar -tzf "$BACKUP_DIR/files.tar.gz" > "$BACKUP_DIR/files-contents.txt"
  git -C .. rev-parse HEAD > "$BACKUP_DIR/revision.txt"
  git -C .. status --short > "$BACKUP_DIR/git-status.txt"
  git -C .. diff --binary HEAD > "$BACKUP_DIR/local-changes.patch"
  cd "$BACKUP_DIR"
  sha256sum database.dump files.tar.gz > SHA256SUMS
  printf 'Резервная копия создана: %s\n' "$BACKUP_DIR"
)
```

Продолжайте только если блок завершился без ошибки. Если `private/media` отсутствует, сначала выясните, куда настроено сохранение файлов; не считайте неполный архив готовой копией. При изменённом `compose.yaml` проверьте, что команды обращаются к нужному проекту и базе.

Архив содержит пароли и пользовательские данные. Не отправляйте его в GitHub. Сохраните ещё одну копию на другом устройстве или диске: каталог на том же сервере помогает при неудачном обновлении, но не при потере сервера. Просмотр списка архива проверяет читаемость, однако не заменяет реальное восстановление; описание инструментов — [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html) и [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html).

## 8. Обновление из GitHub

Разработчик сначала отправляет проверенный код в `main`. Команды на домашнем сервере скачивают уже опубликованный код; сами они ничего не отправляют в GitHub.

### Подготовка

1. Предупредите менеджера о перерыве, попросите сохранить работу и выйти из редактирования.
2. Остановите Next и worker, дождитесь их завершения.
3. Сделайте резервную копию по разделу 7.
4. Проверьте ветку и локальные правки:

```bash
cd "$HOME/apps/promformatech"
git branch --show-current
git status --short
git diff HEAD -- app/next.config.ts
```

Ожидаемая ветка — `main`. Если выбрана другая, не переключайте её автоматически при наличии правок. `.env` и `private/media` игнорируются Git и в обычном `status` не отображаются. После перехода на конфиг из репозитория локальные настройки origin в `app/next.config.ts` больше не нужны; генерация всё ещё может затронуть отслеживаемые файлы. Не стирайте неизвестные изменения без просмотра.

### Скачать и установить

```bash
git pull --ff-only origin main
cd "$HOME/apps/promformatech/app"
pnpm install --frozen-lockfile
pnpm prepare:app
```

Выполняйте команды последовательно, переходя дальше только после успеха. `--ff-only` не создаёт неожиданный merge-коммит на сервере. Если pull требует затереть локальные изменения или сообщает о расхождении истории, остановитесь; `reset --hard`, `git clean` и удаление lock-файла не являются исправлением.

Если pull прошёл при наличии совместимых локальных правок, они сохраняются. Для **однократного перехода с ранее изменённого вручную конфига** можно временно убрать только известную правку `app/next.config.ts`. Выполняйте следующий блок только если эта правка действительно есть, после просмотра diff, успешной копии из раздела 7 и в том же терминале с `BACKUP_DIR`:

```bash
cd "$HOME/apps/promformatech"
(
  set -euo pipefail
  test -s "$BACKUP_DIR/database.dump"
  test -s "$BACKUP_DIR/files.tar.gz"
  git stash push -m 'home-server: next.config.ts before update' -- app/next.config.ts
  git rev-parse refs/stash > "$BACKUP_DIR/server-config-stash.txt"
  git pull --ff-only origin main
)
```

Убедитесь, что stash действительно создан и pull прошёл. Проверьте новый файл:

```bash
git diff HEAD -- app/next.config.ts
git show HEAD:app/next.config.ts
git status --short
```

В нём должны быть вычисление origin из `SERVER_URL`, `allowedDevOrigins` и `experimental.serverActions.allowedOrigins`. Если прежние локальные изменения касались только этих настроек, **не применяйте старый stash обратно**: они уже учтены в новой версии. Копия и идентификатор stash сохраняются на случай сверки. Если были другие настройки, перенесите только их после просмотра diff. Если pull не удался, оставьте stash сохранённым и сначала разберите ошибку. Не заменяйте новый конфиг целиком старой копией. Инструкция со stash выше не предназначена для произвольного грязного дерева.

После разрешения правок выполните `pnpm install --frozen-lockfile` и `pnpm prepare:app` из `app`, если они ещё не выполнены для новой версии.

### Запуск и проверка

Запустите сайт и worker по разделу 5, затем проверьте:

- Главная, продукция, услуги, проекты и контакты открываются.
- Вход менеджера работает, ранее созданный контент и медиа сохранились.
- Новый черновик сохраняется; предпросмотр показывает правки.
- В отдельной приватной сессии посетителя до публикации остаётся прежняя версия.
- После публикации изменения видны посетителю; тестовую правку затем убрали.
- Новое изображение обрабатывается worker и отображается; при изменениях обработки видео проверьте и небольшой видеоролик.
- На телефоне доступны меню и админка; в терминалах нет новых ошибок.

`pnpm seed`, повторное создание владельца, пересоздание тома базы и `pnpm build` для этого сценария не нужны. Если добавились переменные окружения, сравните изменения `.env.example` и вручную добавьте нужные строки в существующий `.env`, не перезаписывая секреты.

### Обновление структуры контента

В текущей конфигурации Payload синхронизирует схему PostgreSQL автоматически вне production: это относится и к домашнему стенду, и к любому CLI-процессу Payload. Поэтому резервную копию делайте **до** запуска новой версии, worker или команд подготовки. При предупреждении об удалении/преобразовании столбцов не подтверждайте действие наугад: разработчик должен проверить перенос существующих данных. Подробнее — [Postgres в Payload](https://payloadcms.com/docs/database/postgres).

Переменные `NODE_ENV=production` и production-миграции не подставляйте в этот сценарий без отдельного плана. Один откат Git не возвращает прежнюю структуру базы.

## 9. Если обновление не запустилось

Остановите новые Next/worker, сохраните текст ошибки без секретов. Если неудачно только скачивание зависимостей, сначала устраните сеть или доступ к registry; не меняйте версии пакетов и lock-файл для обхода ошибки.

Для отката ориентируйтесь на сохранённые вместе `revision.txt`, `database.dump`, `files.tar.gz` и `local-changes.patch`:

1. Сохраните отдельно текущее неудачное состояние, чтобы не потерять изменения после копии.
2. Подготовьте отдельный каталог кода на ревизии из `revision.txt`, установите соответствующие зависимости.
3. Восстановите дамп в **новую отдельную базу** и медиа/окружение в отдельный каталог. Исходную базу и файлы не удаляйте.
4. Направьте восстановленное окружение на новую базу, сохранив соответствующий `PAYLOAD_SECRET`; проверьте origin-конфиг из копии.
5. Проверьте контент, авторизацию и медиа, затем переключите стенд на восстановленный набор.

Это порядок восстановления, а не автоматическая команда отката. Конкретные имена новой базы и каталога нужно выбрать до выполнения, чтобы не перезаписать работающие данные. До реальной проверки восстановления копия не считается проверенной на пригодность к восстановлению.

## 10. Доступ по домашней сети и через интернет

Для локального доступа оба устройства должны находиться в сети с доступом к `192.168.1.130`. Гостевой Wi-Fi может изолировать устройства. В настройках VPN на сервере и клиенте при необходимости разрешите доступ к локальной сети, не отключая VPN целиком.

Узнать адреса сервера и занятые порты:

```bash
ip -4 addr show
ss -ltnp '( sport = :3000 or sport = :3001 )'
```

Слушатель Next должен быть на `0.0.0.0:3001`. `localhost` на телефоне означает сам телефон, поэтому используйте IP сервера. Проброс порта на роутере не нужен; менеджер вне домашней сети по частному IP не подключится. HTTP используйте только в доверенной локальной сети; вне неё нужен защищённый канал доступа.

На текущем сервере UFW был неактивен. Если вы включили его позже и он блокирует доступ, можно разрешить порт только из фактической домашней подсети, например для `192.168.1.0/24`:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 3001 proto tcp
```

Эта команда добавляет правило и не включает UFW. Не меняйте общую политику firewall и SSH в рамках запуска сайта. PostgreSQL наружу не открывайте.

Для временного интернет-доступа ранее использовали Pinggy. Этот режим требует отдельного актуального `SERVER_URL`, перезапуска процессов и доступности туннеля у посетителя. Бесплатная сессия использованного режима ограничена по времени; адрес после перезапуска меняется. В проведённой проверке ссылка работала с VPN и зависала без него. Поэтому для работы дома основной сценарий этой инструкции — прямой LAN-доступ; старые вкладки Pinggy закройте. Постоянный внешний стенд и автозапуск оформляются отдельной настройкой.

## 11. Типичные проблемы

| Симптом | Проверить и сделать |
| --- | --- |
| `pnpm: command not found` | `export PATH="$HOME/.local/bin:$PATH"`, затем загрузить `.bashrc`; проверить выбранный Node.js. |
| На `3000` открывается чужой сайт | Использовать `3001`; чужие контейнеры не останавливать. |
| На сервере сайт работает, на телефоне нет | Адрес сервера, `--hostname 0.0.0.0`, гостевой Wi-Fi, LAN-доступ в VPN и правила firewall. |
| `Blocked cross-origin request` к `/_next/hmr` | Сопоставить hostname из ошибки, `SERVER_URL` и `allowedDevOrigins`; перезапустить Next. Закрыть вкладку старого адреса. |
| `Identifier ... has already been declared` | Удалить повторное объявление из конфига после просмотра diff; не дописывать конфиг вторым полным блоком. |
| `EADDRINUSE` или lock в `.next` | Проверить `ss` и свои tmux-сессии; остановить предыдущий Next этого проекта. Не убивать все Node-процессы. |
| Медиа висит в обработке | Проверить терминал worker, `ffmpeg`, `ffprobe`, свободный диск и ошибку в карточке файла. |
| Ошибка подключения к PostgreSQL | `docker compose ps`, `pnpm db:logs`, правильный порт и согласованные пароли в `.env`; контейнер и том не удалять. |
| После обновления отсутствуют чанки | Проверить, не запущено ли два Next в одной `.next`; перезапустить один процесс и обновить страницу. Кэш сборки при необходимости переименовать только после остановки Next. |
| Страница/медиа обрываются только через публичную ссылку | Сравнить тот же URL на сервере и в браузере с VPN; не менять права на файлы и не пересоздавать контент до проверки сети. |

Команды диагностики без вывода секретов:

```bash
cd "$HOME/apps/promformatech/app"
docker compose ps
pnpm db:logs
```

Просмотр логов базы завершайте `Ctrl+C`: это останавливает просмотр, а не PostgreSQL. Для передачи ошибки достаточно последних строк нужного терминала с удалёнными паролями, cookies и токенами. Полный `.env`, `docker inspect` с окружением и дамп базы для диагностики не присылайте.

## 12. Короткая памятка

**Обычный старт:** `pnpm db:up` → `pnpm prepare:app` → Next на `0.0.0.0:3001`; в другом терминале `pnpm worker`.

**Обновление:** остановить Next/worker → копия базы, медиа и настроек → проверить Git → `git pull --ff-only origin main` → сохранить/объединить локальный конфиг → `pnpm install --frozen-lockfile` → `pnpm prepare:app` → запустить оба процесса → проверить работу менеджера.

**Что хранит контент:** PostgreSQL и `private/media`. GitHub их не резервирует. `.env` с секретами также нужно сохранять отдельно.

Команды сверены с текущим репозиторием; сценарий копирования и восстановления в этом документе на домашнем сервере автоматически не выполнялся. Выполнение остаётся за администратором через его терминал.
