# Подготовка приложения к production: U1–U4

Кодовая часть плана [«Экономное развёртывание ПромФормаТех на VPS с доменом»](../plans/2026-10-22-2044-feat-vps-production-deployment-plan.md). Этот документ описывает контракт приложения перед упаковкой в Docker. Образы, GitHub Actions/GHCR, настройки VPS, Nginx/TLS и внешние копии относятся к следующим этапам U5–U9.

## Сборка без рабочих данных

```bash
cd app
pnpm install --frozen-lockfile
pnpm build
```

`scripts/build.mjs` запускает подготовку токенов, типов и import map, затем штатную сборку Next.js/Turbopack. Дочерние процессы получают только публичные build-значения: недоступный адрес PostgreSQL, известный compile-time placeholder вместо `PAYLOAD_SECRET`, `https://build.invalid` вместо реального домена и отключённую SMTP. Рабочая база и её наполнение сборке не нужны. Секреты не должны передаваться CI через build args.

`getCMS()` запрещает чтение данных в build-фазе. Sitemap, robots и metadata вычисляются при запросе. Кеш sitemap содержит пути, а не абсолютные адреса: смена runtime-домена не оставляет старый домен в файловом кеше.

`pnpm typecheck` использует тот же build-контекст только для `next typegen`, затем выполняет TypeScript. Генерация типов не требует production-домена и не конфликтует с HTTP-адресом домашнего dev-стенда; проверки production-runtime остаются включёнными.

Build-placeholder запрещён в обычном runtime. Не переносите `NEXT_PHASE=phase-production-build` из процесса сборки в окружение web/worker/migrator.

Docker-образ и отсутствие env/media в его слоях проверяются в U5. Успешная сборка исходников не является проверкой готового Linux-образа.

## Runtime-переменные

| Переменная | Назначение |
| --- | --- |
| `NODE_ENV` | Для публичного релиза — `production`; домашний `next dev` оставляет режим разработки. |
| `SERVER_URL` | Единственный канонический origin. В production обязателен HTTPS, в разработке допустим HTTP/IP/порт. Без пароля, пути, query, fragment и wildcard. |
| `DATABASE_URL` | PostgreSQL соответствующей среды; в production схема создаётся миграцией, не через dev push. |
| `PAYLOAD_SECRET` | Собственный секрет длиной не менее 32 символов. Сохранять между обновлениями и при переносе данных. |
| `MEDIA_ROOT` | Постоянный private-каталог медиа; по умолчанию `private/media`. В production это отдельный persistent volume. |
| `APP_PROCESS_ROLE` | `web`, `worker` или `migrator`. Команды worker и миграций выбирают роль автоматически. |
| `FFMPEG_PATH`, `FFPROBE_PATH` | Необязательные пути к бинарникам, иначе используются команды из PATH. |
| `SMTP_*` | Необязательная доставка уведомлений. Отсутствие SMTP не мешает сохранению заявок. |

Node.js — по `.nvmrc`, pnpm — по `packageManager` в `package.json`. Версии существующих библиотек не обновлялись. Прямые зависимости `pg` и `@types/pg` зафиксированы на уже использовавшейся транзитивно версии: они нужны readiness и инструментам переноса без запуска CMS.

Начальные максимумы пула Payload: web — 4 соединения, worker — 3, migrator — 2. У worker одно соединение занимает advisory lock; уменьшать пул до одного нельзя. Dev schema push выполняет только web-процесс; worker не запускает повторную introspection и DDL. Readiness имеет отдельный пул максимум на одно соединение. Общий лимит соединений PostgreSQL уточняется при упаковке и ресурсной приёмке.

## Запуск после подготовки схемы

До включения web выполняются [миграции и, при необходимости, однократный перенос данных](data-migration.md). Автоматический schema push выключен в production.

Для проверки из исходников:

```bash
pnpm start --hostname 127.0.0.1 --port 3001
```

Во втором терминале с тем же защищённым окружением:

```bash
NODE_ENV=production pnpm worker
```

Это команды проверки кода. В U5 их заменяет запуск готовых контейнеров; установка pnpm, исходников и сборка на VPS не требуются по итоговой архитектуре.

При первом запуске пустой мигрированной базы владелец создаётся через `pnpm cms:create-owner`, получая `OWNER_EMAIL` и `OWNER_PASSWORD` из защищённого окружения. Если пользователи переносятся из снимка, дополнительный владелец перед импортом не создаётся. Ручной порядок ввода пароля описан в [инструкции домашнего стенда](home-server.md).

## Healthcheck

| URL | Успех | Отказ |
| --- | --- | --- |
| `/api/health/live` | `200`, `{"status":"live"}`; БД и авторизация не требуются. | Процесс не отвечает. |
| `/api/health/ready` | `200`, `{"status":"ready"}`; доступна БД, production ledger соответствует релизу. | `503`, `{"status":"unavailable"}`, без SQL/секретов/внутренних ошибок. |

Ответы не кешируются. Readiness ограничен общим deadline 3 секунды, соединением 2 секунды и временем SQL-запроса 1,5 секунды. Dev-маркер в production ledger запрещён. Набор ожидаемых миграций задаёт `src/config/migrations.ts`.

При старте проверяются runtime-конфигурация и возможность записи в private-каталоги медиа. Эта файловая проверка не выполняется на каждом HTTP healthcheck. Liveness не является проверкой готовности принимать пользовательские запросы.

## Приём и обработка медиа

HTTP multipart разбирается штатным temp-file parser Payload с backpressure. Временные файлы лежат в `MEDIA_ROOT/uploads`, не в tmpfs и не в публичном каталоге. Сохранение оригинала копирует доверенный серверный temp-файл без `readFile()` всего содержимого. Buffer-путь сохранён для seed/Local API.

Лимит файла остаётся 500 MiB. Общий request limit дополнительно учитывает поля и multipart overhead; устранён прежний неявный предел parser в 50 MiB. На один HTTP-запрос допускается один файл; bulk-интерфейс CMS отправляет отдельные запросы. Лимиты параллельных соединений и дисковая буферизация на Nginx настраиваются в U7.

Исходник финализируется атомарным rename. Пока запись CMS не подтверждена, на диске остаётся pending-маркер. Ошибка HTTP-операции запускает проверку ссылки из БД и очистку непринятого оригинала. Если БД недоступна или ошибка произошла в Local API, worker сверяет pending-маркеры старше часа; без успешной проверки БД файл не удаляется. Temp-файлы parser очищает сам Payload. Оригиналы имеют mode `0600`, private-каталоги — `0700`; контейнеры web/worker должны иметь согласованный UID/GID.

Выбор видео-стратегии выполняется **до** запуска encoder. Совместимый H.264/AAC с допустимыми геометрией, SAR, ориентацией, frame rate и битрейтом remux-ится через `-c copy`. Остальные допустимые источники перекодируются с ограничениями разрешения, frame rate, битрейта и числа потоков. Постер создаётся отдельно. Неизменённый оригинал сохраняется; encode не считается сжатием без математических потерь.

## Остановка и восстановление worker

Один worker на базу удерживает PostgreSQL advisory lock. При SIGTERM/SIGINT он прекращает брать новые задачи и даёт текущей до 30 секунд. Затем останавливает дочерний обработчик, дожидается его закрытия и переводит временный сбой на штатный механизм повторов Payload. Повторы ограничены; плохой входной файл получает явную ошибку в CMS без бесконечного автоматического цикла.

Внезапно оставшиеся `processing`-задачи восстанавливаются только после получения эксклюзивного lock. Повторные аварии учитываются в бюджете попыток. При потере соединения, удерживающего lock, старый worker прекращается сразу, чтобы не продолжать записи параллельно с новым владельцем.

Готовые производные содержат receipt с параметрами результата. Если процесс завершился после финализации файлов, но до обновления CMS, следующая попытка использует эти производные повторно. Уже опубликованные производные не перезаписываются.

`MEDIA_ROOT/worker-heartbeat.json` обновляется каждые 10 секунд, включая время долгой обработки. Это локальный сигнал для будущего мониторинга U8, а не самостоятельное доказательство исправности всей очереди. SMTP по-прежнему допускает повторную доставку при неоднозначном сетевом сбое.

## Проверки перед упаковкой

```bash
pnpm check
pnpm test:media
pnpm test:integration
```

Расширенная проверка одной production-сборки, runtime-доменов и HTTP-upload:

```bash
NEXT_OUTPUT_DIR=.next-verification pnpm build
RUN_PRODUCTION_SMOKE=true pnpm test:integration
```

Интеграционный runner создаёт только собственные базы `promformatech_verification_*` и отдельные медиакаталоги внутри `private/verification`. В конце удаляются только созданные им базы. Рабочая база и её медиа не используются как испытательная площадка. Для полного браузерного регресса отдельно запускается `pnpm test:e2e`, использующий только `promformatech_e2e`.

Измерение cgroup memory peak, проверка Linux native dependencies, предельный файл 500 MiB, самый тяжёлый разрешённый ролик, ресурсный профиль 4 ГБ и настоящий HTTPS-proxy остаются приёмкой U5/U7/U9. Dev-стенд не заменяет эти измерения.
