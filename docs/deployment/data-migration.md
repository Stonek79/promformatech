# Миграции схемы и перенос наполнения

Сценарий U4: создать production-схему на пустой PostgreSQL-базе и однократно перенести одобренное наполнение из согласованного снимка. Поддерживается только совпадающая схема. Инструмент не предназначен для синхронизации двух действующих сайтов или слияния контента.

## Что подготовить

- Исходный неизменяемый снимок PostgreSQL, восстановленный в отдельную базу, и соответствующие `originals`/`derived` из медиахранилища. Для согласованного capture писатели должны быть остановлены.
- Новую целевую базу и пустой целевой медиакаталог. Её DDL-учётная запись используется только оператором/migrator; разделение PostgreSQL-ролей настраивается в U5.
- Совместимый релиз приложения, прежний `PAYLOAD_SECRET` и одобренный runtime-origin.
- Внешнюю копию исходного снимка, достаточное место на диске и закрытый доступ к стенду. Проверка свободного места на будущем VPS входит в инфраструктурный preflight.

Источник переноса нельзя подменять случайной рабочей базой или E2E-базой. Текущий автоматический rehearsal использует искусственный dev-снимок с seed, пользователем, черновиками, заявкой и незавершённой задачей. Настоящее наполнение владельца перед первым выкатом проходит тот же сценарий отдельно.

## Сначала миграции

Настройки целевой среды находятся в отдельном защищённом файле вне Git, mode `0600`. Пример состава, с заменяемыми значениями:

```dotenv
DATABASE_URL=postgresql://migrator:REPLACE_PASSWORD@postgres:5432/promformatech
PAYLOAD_SECRET=REPLACE_WITH_THE_EXISTING_SECRET_AT_LEAST_32_CHARACTERS
SERVER_URL=https://example.com
MEDIA_ROOT=/data/media
```

Команда читает файл через `OPERATIONS_ENV_FILE`; секреты не передаются в аргументах процесса:

```bash
OPERATIONS_ENV_FILE=/secure/path/production.env pnpm db:migrate
```

Wrapper выбирает production/migrator-режим, берёт эксклюзивный operation lock, проверяет текущее состояние, запускает штатный Payload migrator и проверяет ledger после его завершения. Повторный запуск без новых миграций безопасен.

Initial migration `20261022_221745_initial` сгенерирована Payload из текущих коллекций. SQL разбит на упорядоченные файлы до 200 строк без изменения самих statements. JSON рядом с миграцией — машинный snapshot Drizzle для следующих миграций; его не редактируют вручную. После применения initial migration нельзя переписывать её SQL или переиспользовать имя для другой схемы.

Initial migration откажется работать поверх существующих public-таблиц. Wrapper отвергает dev ledger с `batch: -1`, неизвестные записи и несовместимый релиз. Не удаляйте dev-маркер вручную и не применяйте initial migration поверх полного dev dump.

Автоматический `down` initial schema запрещён: он мог бы удалить весь сайт. Возврат данных выполняется восстановлением проверенного снимка в отдельную базу. Команды `migrate:fresh/reset/refresh` не входят в порядок развёртывания.

## Настройки импорта

Дополните тот же защищённый файл:

```dotenv
SOURCE_DATABASE_URL=postgresql://snapshot_reader:REPLACE_PASSWORD@snapshot-host:5432/approved_snapshot
SOURCE_MEDIA_ROOT=/snapshots/approved/media
IMPORT_REPORT_DIR=/secure/import-reports/first-import
```

`DATABASE_URL` и `MEDIA_ROOT` указывают **назначение**, переменные с префиксом `SOURCE_` — источник. Используйте канонические отдельные пути, без symlink в снимке. Для каждого нового импорта выбирайте отдельный каталог отчёта; существующий prepared/committed manifest не перезаписывается автоматически.

Источник читается в `REPEATABLE READ READ ONLY`. Назначение должно содержать правильный migration ledger и не содержать контента. Отвергаются одинаковые source/target базы, разные схемы, циклические зависимости FK без явного преобразования, неполный медиаснимок и непустое назначение.

## Предварительная проверка

```bash
OPERATIONS_ENV_FILE=/secure/path/production.env pnpm cms:import-content
```

Режим по умолчанию не переносит строки и файлы. Проверяются схема таблиц/столбцов/constraints/indexes/enums, целевой ledger и пустота таблиц, источник медиа и checksum. В stdout попадают только режим, fingerprint и количество таблиц/файлов, а не содержимое документов или пароли.

При `Schema mismatch` остановитесь. Требуется согласованное преобразование данных либо снимок правильной версии, а не принудительное отключение проверок.

## Применение

После успешного dry-run, при остановленных web/worker и неизменном снимке:

```bash
IMPORT_CONFIRM=IMPORT_INTO_EMPTY_MIGRATED_DATABASE \
OPERATIONS_ENV_FILE=/secure/path/production.env \
pnpm cms:import-content --apply
```

Инструмент выполняет перенос в порядке FK, ограниченными порциями строк. Для каждой таблицы сверяются количество и SHA-256 упорядоченных строк. Сохраняются ID, пользователи и их данные авторизации, связи, globals, версии/черновики, заявки, media keys и очередь задач. Последовательности восстанавливаются из источника, чтобы следующий ID не конфликтовал с импортированными.

Не импортируются dev migration ledger, KV-кеш, временные блокировки редактирования и счётчики ограничения запросов. У production остаётся ledger, полученный настоящей миграцией. Незавершённая очередь сохраняется; новый worker восстановит её после получения lock. Автоматическая повторная отправка уведомления может дублировать письмо после неоднозначного SMTP-сбоя.

Оригиналы и производные копируются в отдельный private staging, проверяются checksum и затем финализируются rename. HTTP temp, transcode staging и worker heartbeat не являются переносимыми данными. Готовые медиа проверяются также по ссылкам из основной и версионной таблиц: отсутствие используемого оригинала или производной прерывает перенос.

При успехе manifest получает `state: committed`. В target `payload_kv` сохраняется receipt с тем же ID под ключом `promformatech:content-import`. Manifest содержит fingerprint, количества/checksum таблиц и файлов; храните его защищённо вместе с исходным snapshot и указанием релиза.

## Проверка перед включением сайта

1. Убедитесь, что manifest — `committed`, а его ID совпадает с receipt в целевой базе.
2. Проверьте `/api/health/ready` и migration ledger.
3. Войдите прежним владельцем/менеджером, проверьте версии и сохранённые черновики.
4. В отдельном гостевом браузере проверьте опубликованное наполнение и закрытые оригиналы/черновики.
5. Запустите worker, проверьте завершение старых задач и новую загрузку.
6. Выполните сохранение/предпросмотр/публикацию и создание новой записи; старые материалы должны сохраниться.

Owner CLI нужен только если пользователей не переносили и владельца действительно нет. Seed после импорта не запускается.

## Ошибка или прерывание

При SQL-ошибке транзакция строк откатывается. Исходник не изменяется. Оператор не должен повторно выполнять импорт поверх уже заполненной базы.

Файловый rename и COMMIT PostgreSQL не являются одной общей транзакцией. Поэтому до записи создаётся manifest `prepared`, а внутри SQL-транзакции записывается receipt. Если процесс оборвался:

- `prepared` и нет receipt: остановите писателей, проверьте пустоту целевой базы и наличие финализированного медиакаталога. Сохраните аварийное состояние. Новый запуск выполняйте в новом пустом назначении; существующие файлы автоматически не удаляются.
- Receipt существует с ожидаемым ID, но manifest всё ещё `prepared`: COMMIT мог уже состояться. Проверьте количество/checksum данных и завершите проверку по receipt; повторный импорт не запускайте.
- `committed`: перенос завершён; ошибка последующего запуска приложения не является основанием автоматического восстановления старых данных.

Состояние sequence не транзакционно в PostgreSQL: при неудачной попытке её счётчик может сдвинуться, даже если строки откатились. Безопасный путь после неоднозначного сбоя — новое пустое назначение и повтор из неизменного снимка.

## Автоматическая репетиция

```bash
pnpm test:integration
```

Runner создаёт случайно именованные временные базы, генерирует dev-источник, выполняет initial/repeat migrate, dry-run и реальный импорт, проверяет авторизацию, версии, очередь, checksum и выдачу ID. Отдельно проверяются отказы при dev-маркере, несовпадении схемы и повторном импорте. В конце удаляются только созданные runner базы. Секреты тестов не сохраняются в отчёт и не выводятся.

Production HTTP и остановка worker проверяются расширенным сценарием из [runtime-инструкции](runtime.md). Настоящий перенос выбранного владельцем наполнения и восстановление из внешней копии остаются контрольными точками первого выката.
