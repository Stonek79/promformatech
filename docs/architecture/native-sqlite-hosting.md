# Экономный выпуск без Docker: вариант для MVP

Дата: 30.10.2026. Предложение учитывает уточнение владельца: production ещё не запущен, перенос рабочего наполнения PostgreSQL → SQLite не нужен. Код переведён на SQLite. Актуальные команды и ограничения — в [инструкции VPS](../deployment/native-vps.md).

## Рекомендация

Для одного небольшого сервера и нескольких редакторов подходит Next.js + Payload + SQLite. Использовать официальный `@payloadcms/db-sqlite` той же версии, что остальные пакеты Payload; версии Next/React/Payload не менять попутно. Файлы медиа хранить отдельно от SQLite и от каталога релиза. Публичную форму владелец исключил, поэтому интенсивного потока записей от посетителей не ожидается.

SQLite встроена в процесс приложения, отдельный сервер базы не запускается. Payload предоставляет SQLite-адаптер, WAL и настройку ожидания блокировки `busyTimeout`. Черновики, версии, связи и jobs должны оставаться штатными механизмами CMS. [Документация Payload](https://payloadcms.com/docs/database/sqlite).

WAL позволяет читателям работать параллельно с записью, но одновременно записывает один writer. Для нас это требует коротких транзакций и проверки совместной работы менеджера и worker. Режим WAL требует локального файла, доступного процессам на одной машине; общая база на NFS и несколько VPS с одним файлом не входят в эту архитектуру. [SQLite WAL](https://www.sqlite.org/wal.html).

Переход не нужен ради количества фотографий: сами фото/видео лежат в файловом хранилище, база хранит метаданные и связи. SQLite уменьшит число фоновых сервисов, но не ограничит автоматически память Sharp/FFmpeg или Node.js.

## Процессы и каталоги

| Часть | Запуск и назначение |
| --- | --- |
| Nginx | HTTP/HTTPS, сертификат, лимиты, streaming/range; проксирует на внутренний порт |
| Web | Один production-процесс Next.js/Payload под `systemd`; слушает только loopback за Nginx |
| Worker | Отдельная служба; один тяжёлый файл за раз, ограниченные CPU/RAM и graceful stop |
| SQLite | Постоянный файл в shared-каталоге, WAL, ограниченный timeout ожидания записи |
| Медиа | Постоянный shared-каталог исходников/производных/временных файлов |
| Backup | Согласованный снимок SQLite и медиа, шифрованная внешняя копия, timer и restore-проверка |
| Releases | Неизменяемые каталоги по commit SHA; код не содержит DB/media/.env |

Для редких загрузок можно запускать уже существующий `worker:once` через `systemd.timer`: после выполнения процесса его память освобождается. Сейчас один проход обрабатывает не более одной задачи в каждой очереди. Цена экономии — ожидание очередного запуска и меньшая скорость разбора большой пачки. При постоянных массовых загрузках нужен обычный worker; выбор определяется замером.

Docker Desktop на Mac запускает Linux VM, тогда как контейнеры используют изоляцию процессов и общее ядро. Поэтому расход Docker Desktop нельзя напрямую переносить на оценку native Linux VPS. Отказ от Docker оправдан упрощением небольшого хоста, но не является доказательством большого ускорения приложения. [Docker VMM](https://docs.docker.com/desktop/features/vmm/), [контейнеры и VM](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/).

## Сборка и обновление

1. GitHub Actions проверяет lockfile, типы, тесты и собирает Linux-релиз под архитектуру/среду целевого хоста. Native Sharp/libSQL должны соответствовать Linux; артефакт, собранный на Mac, на VPS не переносится.
2. Для web упаковывается standalone-вывод Next, включая static/public. Отдельно готовятся исполняемые worker и команды Payload: web tracing не заменяет упаковку всех CLI entry points. FFmpeg устанавливается на сервере. [Next output](https://nextjs.org/docs/app/api-reference/config/next-config-js/output).
3. На VPS передаётся готовый архив с manifest/checksum. Установка зависимостей и сборка на VPS не выполняются; `.env`, SQLite и медиа не включаются в архив.
4. Архив распаковывается в новый каталог релиза. На малом VPS обновление использует короткое окно обслуживания: остановить worker, остановить web, сделать согласованную копию данных, применить необходимые миграции схемы, переключить релиз, запустить web, проверить readiness, вернуть обработку очереди.
5. Предыдущий артефакт хранится для возврата совместимого кода. Несовместимые изменения схемы не исправляются автоматическим возвратом старого файла БД поверх новых данных.

Один production-процесс и короткое окно обновления экономнее параллельного запуска старого и нового web на тесном хосте. Если потребуется обновление без простоя, его дополнительный пик памяти нужно включить в требования к серверу.

## Реализация

Официальный SQLite-адаптер установлен без обновления остальных библиотек. PostgreSQL Pool/advisory locks, Docker Compose и перенос старой базы удалены. Включены WAL, busyTimeout, blocksAsJSON. Создана новая исходная миграция; dev/E2E используют свои файлы. Добавлены standalone, CLI-пакет, Linux CI и шаблоны systemd/Nginx/backup. Схемы удалённой формы не переносятся. Старые локальные БД и медиа не удаляются.

## Что измерить до выбора минимального VPS

- Суммарные RAM/PSS и CPU web, worker, Nginx и ОС, а не только V8 heap одного процесса.
- Пик при входе в админку, сохранении/публикации, загрузке и самом тяжёлом допустимом видео.
- Задержки чтения/сохранения при одновременной работе менеджера и worker; ошибки `SQLITE_BUSY`.
- Пики во время выката, снятия копии и восстановления; свободный диск для оригинала, производных, temp, WAL, релизов и backup.

Замеры на целевом Linux обязательны перед обещанием конкретного объёма RAM. Сборку и видео оцениваем отдельно: перенос сборки в CI убирает её пик с VPS, а обработка видео остаётся runtime-нагрузкой.

Живую SQLite нельзя резервировать простым копированием только основного файла при активном WAL. Использовать поддерживаемый backup API/`.backup` или согласованную остановку писателей, затем копировать вместе с медиа и проверять восстановление. [SQLite backup](https://www.sqlite.org/backup.html).
