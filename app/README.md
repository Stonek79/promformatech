# ПромФормаТех

Корпоративный сайт-витрина: Next.js 16, React 19, Payload 3 и PostgreSQL 17.
Публичные страницы, русская админка менеджера и фоновые задачи находятся в одном
приложении. Next.js запускается локально, PostgreSQL — в Docker. Перенос
действующего домена и развёртывание production в эту поставку не входят.

## Запуск

Для домашнего тестового сервера с доступом из локальной сети:
[установка, запуск, обновление и резервные копии](../docs/deployment/home-server.md).
Адрес стенда задаётся через `SERVER_URL` в `.env`: Next.js автоматически получает
из него разрешённые origin для dev-ресурсов и Server Actions. После смены адреса
перезапустите приложение; править `next.config.ts` на сервере не нужно.

Требуются Node.js 22.22.0, pnpm 10.12.4, Docker Engine. Для видео — `ffmpeg` и
`ffprobe` в PATH (либо переменные `FFMPEG_PATH` и `FFPROBE_PATH`).

Из каталога `app`:

```bash
pnpm install --frozen-lockfile
pnpm env:init
pnpm db:up
pnpm seed
pnpm dev
```

Сайт: <http://localhost:3000>. Админка: <http://localhost:3000/admin>.
При первом локальном входе создайте владельца. После этого владелец добавляет
менеджера в разделе «Пользователи». В production публичная регистрация первого
владельца запрещена: используйте `pnpm cms:create-owner`, передав `OWNER_EMAIL`
и `OWNER_PASSWORD` через защищённое окружение. Не сохраняйте пароль в истории команд.

Для новых загрузок и уведомлений во втором терминале:

```bash
pnpm worker
```

Worker обрабатывает по одному тяжёлому файлу, хранит очередь в PostgreSQL,
защищён от запуска второго экземпляра на той же базе и возобновляет задачи после
аварийного завершения. `pnpm worker:once` выполняет один проход и завершается.
Останавливайте процессы через Ctrl+C. Чтобы освободить память после работы,
остановите dev/worker и выполните `pnpm db:down`. Том базы сохраняется.

`env:init` создаёт `.env` со случайными секретами, сохраняя существующий файл.
`seed` добавляет исходные материалы и изображения, **не перезаписывая** найденный
контент и не создавая пользователей. `seed-assets` содержит начальные исходники;
новые загрузки хранятся только в `private/media`, вне публичного каталога.
Шрифт Unbounded сохранён локально вместе с лицензией OFL; Google Fonts при
запуске и сборке не используется.

## Возможности менеджера

- Страницы и главная: готовые блоки, порядок и видимость, тексты, изображения,
  видео, галереи, этапы, характеристики, карточки материалов, форма связи.
- Продукция, услуги, проекты: выставочные материалы без торговых полей.
- Общие данные: логотипы, контакты, меню, подвал, подписи интерфейса и формы, SEO.
- Фото и видео: исходник, готовность обработки, ошибка и повтор. Заменяйте файл
  новой загрузкой; исходник существующего материала не перезаписывается.
- Заявки: исходное обращение, статус, комментарий, состояние уведомления.
- Черновики, версии, предпросмотр и явная публикация. Сохранение черновика не
  заменяет опубликованный снимок. Формы в режиме предпросмотра не отправляются.

Менеджер не управляет ролями, секретами, служебными настройками и физическим
удалением файлов. Поля «Дополнительно» предназначены для осознанного изменения
адресов и SEO. Адреса задаются английскими словами без `.html`; автоматической
транслитерации и совместимости со старой схемой нет.
Краткая инструкция: [руководство менеджера](../docs/admin/manager-guide.md).
Подробная справка доступна прямо в админке: **Помощь менеджеру**, `/admin/help`.
Переключатель с солнцем/луной меняет тему, кнопка **T ↕** циклически меняет размер текста.
Модальные окна и списки не используются. Предпочтения
сохраняются в браузере отдельно для каждой поверхности и не меняют CMS-контент.

## Медиа

Фото: JPEG, PNG, WebP, AVIF; до 40 млн пикселей, без анимации. Автоматически
готовятся WebP нескольких размеров. Видео: MP4/MOV/WebM, до 500 МБ, 15 минут и
4K на входе; H.264/AAC до 1080p, постер и HTTP Range. Увеличения разрешения нет.
Параметры находятся в `src/config/media.ts`. Обработка с потерями подобрана для
визуального качества, математическую «без потери качества» она не обещает.
Неизменённый оригинал хранится отдельно и доступен только сотруднику.

Анонимный доступ к производным разрешён только при наличии опубликованного
материала с этим файлом. После отмены публикации доступ закрывается; файлы
не сохраняются в публичном CDN или кэше Next Image. Браузер уже скачавшего файл
посетителя, разумеется, не может быть отозван сервером.

Изображения фасада используют `next/image`: собственный loader выбирает уже
подготовленные worker версии 480/960/1600 px, `sizes` соответствует сетке.
Повторное сжатие через `/_next/image` не выполняется: браузер обращается к
защищённому media-маршруту напрямую, сохраняя доступ к черновикам в preview.
Видеопостер также использует `Image`, с `unoptimized` для готового постера.

## Проверки

```bash
pnpm check
pnpm test:e2e
pnpm test:media
pnpm test:integration
pnpm build
```

`check`: Biome, Next route types, TypeScript, Stylelint, токены и Vitest.
`test:media` отдельно проверяет Sharp и настоящий FFmpeg/ffprobe.
`test:integration` создаёт отдельные временные базы и медиакаталоги для initial
migration, переноса данных, проверки владельца, версий, очереди и ID. Рабочая
база не используется для испытаний. Расширенная production-проверка описана
в [runtime-контракте](../docs/deployment/runtime.md).
`test:e2e`: Chromium (`pnpm exec playwright install chromium`), отдельная БД
`promformatech_e2e`, порт 3100 и каталог `.next-e2e`. Команда пересоздаёт **только
эту тестовую базу** и `private/e2e-media`; рабочую базу не использует. Сервер и
браузер завершаются после тестов. Трассы ошибок остаются в `test-results`.
Не запускайте проверки одновременно с другим Next-сервером этого приложения.

`dev`/`build` генерируют токены, Payload types и import map. После правок схем
можно вызвать `pnpm prepare:app` отдельно. Генерируемые файлы не редактируются
вручную. UI kit доступен сотруднику по `/ui-kit` только вне production.

## Данные и окружение

PostgreSQL слушает только `127.0.0.1:5433`. Параметры — в `.env`. При изменении
порта обновите одновременно `POSTGRES_PORT` и `DATABASE_URL`. Смена значения
пароля в `.env` не меняет пароль уже созданного пользователя PostgreSQL.
`docker compose down --volumes` удаляет данные; для обычной остановки не нужен.
Именованный Docker-том **не заменяет резервную копию**.

В разработке схему синхронизирует web-процесс Payload; worker использует уже
созданные таблицы. В production schema push выключен. Подготовлены initial
migration и защищённая команда `pnpm db:migrate`; существующее наполнение
переносится data-only в новую мигрированную базу. Порядок и ограничения:
[миграции и перенос данных](../docs/deployment/data-migration.md).
До переключения домена требуется проверка восстановления.
Сохранять нужно PostgreSQL, весь `private/media`, конфигурацию и секреты
отдельно от сервера. Внешний backup и реальное восстановление пока не подключены.

Необязательная почта: `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, `SMTP_FROM_NAME`,
`SMTP_USER`, `SMTP_PASSWORD`; получатели — в служебных настройках владельца.
Без SMTP заявки остаются в CMS, а не теряются. Доставку и восстановление пароля
нужно проверить после подключения SMTP. Повтор после сбоя SMTP допускает
повторное письмо, если сервер успел принять предыдущее до разрыва соединения.

`pnpm cms:cleanup` показывает число старых закрытых заявок/спама к удалению;
`pnpm cms:cleanup apply` выполняет очистку по сроку из служебных настроек и
удаляет истёкшие счётчики частоты. Новые и находящиеся в работе заявки сохраняются.

За reverse proxy доверять клиентскому IP можно только при `TRUST_PROXY_HEADERS=true`
и гарантированном перезаписывании `X-Real-IP` доверенным proxy. Без этого локальный
лимитер считает обращения общим источником. Публичный хост потребует HTTPS,
сетевой защиты провайдера/CDN и ограничения доступа к origin: код приложения
сам по себе не защищает канал сервера от объёмного DDoS.

## До публичного запуска

Владелец подтверждает телефон, почту, адреса и содержимое. Сейчас основной телефон
взят из контактов исходного сайта (Джек); проекты не выдуманы. Правовая страница
`privacy` оставлена черновиком для заполнения владельцем; её нужно подготовить
и опубликовать до публичного приёма обращений. Нужны также SMTP, production-
окружение, миграции, offsite backup с restore-проверкой и приёмка менеджером.
Данные с production не должны попадать в тестовую базу.

Исходники можно хранить в GitHub, но GitHub Pages не запускает Payload,
PostgreSQL и worker. Для полной проверки нужен работающий Node.js-хост.

Структура модулей: [архитектура](../docs/architecture/application-structure.md).
Тексты и подготовка переводов: [локализация](../docs/architecture/localization.md).
Разработка и production-сборка используют встроенный Turbopack из Next.js.
Отдельный сборщик приложения не нужен. Медиа хранятся в runtime-томе и не
включаются в файловую трассировку сборки.

Кодовая подготовка к экономному VPS: [runtime-контракт U1–U4](../docs/deployment/runtime.md).
`pnpm build` использует недоступную БД и публичные build-placeholders; данные
CMS и настоящий домен читаются в runtime. Production-запуск требует реальных
секретов и HTTPS `SERVER_URL`; для домашнего HTTP-стенда используется `next dev`.
Маршруты `/api/health/live` и `/api/health/ready` доступны без входа, readiness
проверяет production migration ledger. Docker-образы и CI/CD поставляются в U5–U6.

Правила кода проверяются автоматически: блоки условий, запрет явного `any`,
константы для числовых лимитов и максимум 300 строк в файле кода. Типы CMS
генерируются командой `pnpm payload:types` в `src/payload-types/`; менять их
вручную не нужно. Генерация сохраняет реальные имена коллекций и связывает
ключи `Config` с константами.

Проверка работы менеджера: [покрытие админки](../docs/admin/verification.md).
Для отдельного сценария: `pnpm test:e2e admin-pages.spec.ts`. Тесты используют
отдельную БД, отдельное хранилище и отключённую SMTP.
